## Milestone 1 — account, chats, and server compatibility

Implement signup, sign-in, password visibility, profile name and protected avatar, email change, in-session password change, password recovery by email link and six-digit code, sign-out, and the separate emailed history unlock. Use one persistent random installation UUID excluded from device backup/restore. Put it in `X-App-Device` on signup/sign-in and reuse it as `deviceId` for call actions. Store the session using Android Keystore-backed protection, keep user-scoped local data isolated, and purge credentials/media on auth revocation. A different installation can sign out the older session and lock earlier history without deleting it. Check `historyLocked` before showing cached content.

| Key account operation | Contract |
|---|---|
| Sign up | `POST /api/app/account/register` with `{name,email,password,passwordConfirm}` and the device header. Save `{token,record}` |
| Sign in/refresh | `POST /api/collections/users/auth-with-password` with `{identity,password}` and the device header. Restore/refresh existing auth with `POST /api/collections/users/auth-refresh` |
| Auth header | `Authorization: <PocketBase auth token>` for authenticated requests |
| History | `GET /api/app/account/session` returns `{historyLocked}`. Send `POST /api/app/account/history/request` with `{}` and `.../history/confirm` with `{code}` |
| Recovery OTP | `POST /api/app/account/recovery/request` with `{email}`. Confirm at `.../recovery/confirm` with `{email,code,password,passwordConfirm}`, then sign in |
| Change password | `POST /api/app/account/password` with the two matching new passwords. Atomically save the returned replacement auth token |
| Email change and recovery link | Request through the documented PocketBase auth endpoints and use the existing HTTPS pages in a Custom Tab for link confirmation. Refresh auth or sign in as appropriate on return |
| Profile | Update the signed-in record at `PATCH /api/collections/users/records/{id}` and use multipart for avatar. Get protected file tokens through the file API |
| Logout | Remove own push registration first, invoke `POST /api/app/account/logout`, then clear session and client state |

Build inbox, search by name or exact email, sent/received requests and accept/decline/cancel. Use `GET /api/app/inbox`, `GET /api/app/members/search?q=…`, `POST /api/app/message-requests` with `{recipient,note?}`, `POST /api/app/message-requests/{id}/accept`, and `DELETE /api/app/message-requests/{id}`. Show the existing chat when returned. After acceptance the server owns chat creation and moves an optional first note into the conversation.

Support text, replies, own edits, image/video/voice attachments, read-through, typing/presence and the seven common emojis plus custom keyboard emoji. A user can replace or remove their one reaction on a message. Route writes through the documented Go endpoints. Reuse the same `client_message_id` over network retries, merge by record ID and present success as server receipt. Use the system photo picker, record interoperable voice notes and validate an actual upload. For media, stream or fetch protected files with `POST /api/files/token`, use thumbnails, and handle expired links and upload limits correctly.

Subscribe with PocketBase's `GET /api/realtime` and authenticated `POST /api/realtime` with `{clientId,subscriptions}`. Use collection topics and the current token, merge create/update/delete events, resync after reconnect and resume, and retain a REST fallback. Page 30 messages by `(created,id)` in either direction. Respect the server's auth, visibility and history rules. Avoid a permanent background SSE connection as a push substitute. [PocketBase realtime protocol](https://pocketbase.io/docs/api-realtime/)

## Milestone 2 — WhatsApp-style Android calling

Implement one session-scoped call coordinator shared by Compose, FirebaseMessagingService, notification actions, Android Core-Telecom and LiveKit. Use an explicit state machine for ringing, answering, connecting, active, reconnecting and ended. Serialize events by call ID so duplicate FCM/SSE events, multiple taps, notification callbacks and headset actions cannot create multiple calls or rooms. Keep the coordinator alive through activity recreation and ongoing calls with a foreground service as required. The current backend serves one-to-one calls.

### Push and incoming call experience

1. Once signed in, check `GET /api/app/push` and register using `POST /api/app/devices` with `{platform:"android",token}`. Hold the server record ID. Handle `onNewToken`, replacement and sign-out cleanup. Preserve ownership across account changes.
2. Parse the FCM data fields `event`, `id`, `expiresAt`. The server sends high-priority `incoming_call` with a call ID and a roughly 45-second ring window, plus normal-priority `new_message` with a **conversation ID**. Discard stale events. Deduplicate ringing by call ID and group message notifications by conversation, while allowing later messages to update that group.
3. Post an eligible call notification promptly with generic privacy-safe content, then revalidate via authenticated `GET /api/collections/calls/records/{id}`. Show the caller only after an authenticated lookup and according to lockscreen privacy. Use `NotificationCompat.CallStyle` with Answer/Decline and an ongoing call notification with End. Use high-importance incoming-call and appropriate message channels, with consistent notification IDs. On eligible Android versions/configurations use the full-screen incoming UI for a locked device. Check `canUseFullScreenIntent()` on supported versions and provide the heads-up/actionable notification fallback. Honor Android notification permission, user channel settings, Doze and manufacturer restrictions. Explain in help that OS force-stop is a separate state from closing Recents.
4. Integrate self-managed Core-Telecom with `CallsManager`. Add the call to Telecom once, post its CallStyle notification within the platform deadline, and handle remote surface callbacks within their deadlines. Use the proper foreground service types and permissions for an ongoing call and for mic/camera access when required. Apply platform while-in-use rules. Keep media capture off while merely ringing. From lockscreen/background, fall back to an audio answer or a user-visible permission flow where supported.
5. If the call is cancelled or expired, clean up the ringtone, Telecom slot and notification. The backend currently emits no cancellation/terminal push. Use SSE where available, the server expiry timer and a fresh authenticated state check for notification actions. Document a terminal push event as a future backend enhancement. [Core-Telecom](https://developer.android.com/develop/connectivity/telecom/voip-app/telecom) · [Foreground services](https://developer.android.com/develop/background-work/services/fgs/service-types) · [Android FCM priority](https://firebase.google.com/docs/cloud-messaging/android-message-priority)

### Call actions and room behavior

Use these paths under `/api/app`.

- Start with `POST /calls` and `{conversation,kind:"audio"|"video"}`.
- For Answer, verify the call still belongs to the signed-in recipient and is ringing. Call `POST /calls/{id}/accept` with `{deviceId}` and only then obtain `POST /calls/{id}/token` with the same device UUID. The caller waits for accepted or connected state before fetching a grant. Join the returned `wsUrl` using its five-minute JWT. Never put grant tokens in logs or saved notification data.
- Reject while ringing through `/reject`. Cancel outgoing ringing or end an accepted/connected call through `/end`. Reconcile 404/409 and expiry against authority. Join one room and disconnect/clean up exactly once. On connectivity changes let LiveKit reconnect first and get a fresh token only when a new join is required and the call is still valid.
- In-call text chat uses `POST /messages` with `in_call:true`. Show recent chat and preserve the draft on layout transitions. LiveKit carries audio/video and screen-share media. PocketBase carries all persistent messages.

## Milestone 4 — optional Secure Mode during calls

Add a lock icon to active audio and video calls. Every call starts with Secure Mode off, with the usual capture behavior allowed by the OS. Either participant can turn the mode on. The server grants ownership to the first successful enabler and applies that state to both participants. Only that owner can turn it off. Once off, either participant can enable a new activation. Show who enabled it and explain why the other participant's control is locked. Clear the UI and call-scoped protection at hang-up.

This feature requires a backend extension. Implement against the proposed contract in the context file, with a participant-authenticated atomic state update, revision checks, acknowledgements per device and authenticated call-state synchronization over SSE and REST. Require both clients to declare supported capabilities for the active call. Keep the lock action unavailable for web, older app versions and unconfirmed peers. The existing service has no Secure Mode route. Deliver the proposed migration/route as a separate backend change for review, and enable the real control only after a compatible backend and peer are available.

Apply `FLAG_SECURE` immediately on the enabling device and on the other device when it receives the authoritative state. Keep protected windows covered through rotation, minimize, background and recreation. Verify secure PiP on physical devices. Hide protected PiP video or disable PiP if it cannot be covered. Stop any active in-app screen share before acknowledging and block new sharing while enabled. Use a restrictive playback capture policy for call audio where the Android version and media SDK support it, and verify audio separately. Keep an applying state until both devices acknowledge the current revision. Preserve any applied protection through reconnect until a valid owner-authorized off state arrives or the call ends. Explain that this reduces ordinary screenshots and screen recordings on supported Android devices and that external recording or modified devices can still capture the call. [Android FLAG_SECURE](https://developer.android.com/security/fraud-prevention/activities) · [Android audio playback capture](https://developer.android.com/media/platform/av-capture)

Test both roles, simultaneous enables, owner-only disable at the API, stale updates, recording already in progress, screenshot and recording on both phones, PiP and recent-app previews, process recreation, reconnect, screen-share shutdown, unsupported peers, and reset to off on the next call.
